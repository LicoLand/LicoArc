# Lico Arc Protocol Specifications

This directory is the canonical source of Lico Arc Protocol field semantics,
versioned contracts, and deterministic governance rules.

## Canonical field authority

The [Canonical Field Registry](FIELD-REGISTRY.md) is the sole normative
authority for the active logical field inventory. It owns every active field's
name, object or operation, semantic type, presence, visibility, normative
rule, direct contribution to the LicoArc final vision, and excluded or
profile-owned disposition. Its `Detailed
description（详细说明）` links lead to non-normative field-specific records that
explain role, vision contribution, field model, alternatives, comparative
evidence, and decision history.

Versioned schemas and registries under `vN/` define or project a Protocol
Line. They cannot add, remove, rename, relocate, or reinterpret an active field
unless the Canonical Field Registry is changed through the Decision Lifecycle
in the same complete migration. Any definition mismatch is reported by
`docs/STATUS.md`; no projection becomes a second field authority.

## Lifecycle

Each protocol line is isolated under `spec/vN/`. A line may be:

- **Draft** — design work kept outside the tracked specification tree.
- **Candidate** — tracked sources and generated bytes may change through
  review and regeneration.
- **Published** — an immutable, content-addressed protocol definition.
- **Retired** — no longer recommended for new deployments, while an already
  published artifact remains verifiable.

The repository currently contains the Candidate `v1` Protocol Line. Its
explicit source manifest is [`v1/manifest.json`](v1/manifest.json). The
manifest and generated bundle both declare exact wire ID
`licoarc.protocol-line.v1` and lifecycle `Candidate`; the bundle digest binds
those fields and all embedded sources. Its definition status is `COMPLETE`, it
is eligible for authenticated new-session selection, and publication remains
separately unauthorized. This content addressing pins one exact Candidate
snapshot without making the Candidate line immutable.

## Definition composition

The v1 manifest binds the complete Protocol Line definition, including the
foundation, identity, protection, messaging, Group, reliable exchange,
evidence, transport, and governance source families. Each
capability's schemas, registries, policies, bounds, and definition-level
positive and negative corpus describe exact protocol meaning; none is runtime
or delivery evidence.

Pairwise Protection is defined in its own v1 profile sources. Endpoint
implementations hold private keys and execute the pinned profile downstream.
The machine policy preserves the permanent security posture without granting
a Station security authority.

## Capability layout

Specifications are grouped by capability rather than file format:

```text
spec/vN/
  manifest.json
  requirement-registry.schema.json
  <capability>/
    source-manifest.json
    *.schema.json
    registry.json
    *.policy.json
    *.cddl
```

Human-readable projections live under `docs/protocols/`; executable examples,
negative cases, and requirement-evidence mappings live under `conformance/`;
generated consumer bundles live under `artifacts/`.

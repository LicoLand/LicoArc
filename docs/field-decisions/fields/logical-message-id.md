## Question

What exact protected identifier represents one logical intent independently of
transport attempts, Outer Envelopes, routes, and confirmations?

## Role in communication

The sender allocates a logical identity. The receiver uses it for durable
deduplication and supplies it as an idempotency input to the application.
Retries preserve it. A route change may create new transport state without
creating a second logical Message. Each attachment chunk preserves its own
Message identity; a changed Attachment Receive State snapshot receives a new
identity while retry of the same snapshot preserves it.

## Contribution to LicoArc's final vision

Keeps one protected intent stable across retry, restart, re-protection, and
route migration so deduplication does not duplicate effects.

## Field model and trade-offs

| Dimension | Assessment |
| --- | --- |
| Security | ID collision, reuse, spoofing, and conflict between same ID/different protected intent must fail closed. |
| Privacy and metadata | Protection hides the identifier; endpoint persistence still reveals history locally. |
| Interoperability | Generation scope, equality, retry, conflict, expiry, and tombstone rules must be exact. |
| Implementation complexity | Requires bounded durable inbox/outbox indexes and deletion obligations. |
| CPU, memory, and wire cost | Identifier bytes are small; deduplication state is the material cost. |
| Evolution and downgrade | Meaning must survive route changes but cannot be reinterpreted across incompatible Protocol Lines. |

## Necessity proof

| Test | Finding |
| --- | --- |
| Required action | Detect duplicate delivery under at-least-once retry and correlate protected confirmations to one intent. |
| Removal consequence | Duplicate packets can authorize duplicate processing or require unsafe content comparison. |
| Derivation | A hash of ciphertext changes under re-encryption and leaks equality if exposed; a content hash has different semantics. |
| Lower-layer carrier | Transport request or envelope IDs do not survive route change and are Station-visible. |
| Protected placement | Identity must be endpoint-authenticated and hidden from Stations by default. |
| Duplicate-authority risk | Message ID must be distinct from request correlation, stream position, transport resource, and application business key. |

## Value model

The semantic value is a 16-octet unpredictable identifier generated by the
sender within an explicit Endpoint relationship. It stays stable for one
logical intent while profile constants bound deduplication and tombstone
retention. The same attachment chunk retains the value across restart and
Route migration. Reuse with different chunk bytes, index binding, protected
intent, or receive-state snapshot fails closed.

## Alternatives

- Random protected identifier.
- Counter scoped to an authenticated relationship, which adds persistent
  monotonic state.
- Content digest, rejected as the default because equal content is not
  necessarily equal intent and hashing can expose oracles.
- Application idempotency key alone, rejected because generic delivery cannot
  require every application to define one.
- Transport envelope ID, rejected because route and authority differ.

## Decision history

The original decision admitted stable protected identity while leaving its
representation open. The Canonical Field Registry selected unpredictable
`ID128`, stable across retry, re-protection, and route change. Candidate work
still fixes generation procedure, state bounds, conflict handling, and
conformance vectors.

LicoArc review on 2026-08-03 closed the persistence role for attachment
recovery: chunk Message identity survives retry and migration, and a repeated
receive-state `messageId` is processed idempotently without extending any
`ATTACHMENT_RECOVERY_WINDOW` boundary. An older non-empty request cannot reopen
an attachment after authenticated completion or another terminal result.
